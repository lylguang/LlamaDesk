# 开发规则（每次派发都必须遵守）

你在一个隔离的 git 工作树里干活：`/home/xixi/Git/OmniStudio/.claude/worktrees/agent-optimize`
所有路径都相对这个目录。运行时是 bun 1.4.2。

## 不可违反的边界

1. **只改任务说明里「允许改动的文件」列出的那几个文件。** 其它任何文件都不许改、不许建、不许删。
2. **不要执行任何 git 命令。** 不提交、不切分支、不 stash、不 checkout。提交由调度方做。
3. **源码改动要最小。** 只改为达成本次目标所必需的行。顺手重构、顺手改格式、顺手改别的 bug —— 全都不要做。
4. **不要新建计划文件、总结文件、README。** 交付物就是代码加测试，外加一段汇报正文。

## 做法

5. **先红后绿，并留下证据。** 顺序固定：先写会失败的测试 → 跑一次、把失败输出留在汇报里 → 再改源码 → 再跑一次、把通过输出留在汇报里。不要反过来。
6. **每次编辑现有测试文件之后，立刻数一遍用例数量**，和编辑前对比。数量减少 = 你删了别人的用例 = 立即恢复。现有用例只有在任务说明明确允许时才可以改。
7. **测试要真的能抓住这个缺陷。** 自检方法：把你改的源码那几行还原成原样，你新写的用例必须变红。如果还是绿的，说明用例是空转的，重写。
8. **同一个失败换 3 种做法还过不了，就停手汇报**，写清卡在哪、试过什么。不要继续磨。
9. 不确定的地方，按任务说明里写的来，不要自己发挥。任务说明没写到的，在汇报里提出来，不要擅自决定。

## 交付前必做

10. 跑验收门（`<门命令>` 在任务说明里给出），**把它的完整输出原样贴进汇报**，一个字都不要改写、不要概括。
11. 门里出现 `RESULT FAIL` 就是没做完，先修好再交付。修不动就按第 8 条停手汇报。

## 汇报格式（严格按这个结构，标题一字不差）

```
## 交付汇报

### 1 改了什么
（逐个文件说：文件路径、改了哪个函数、改成什么语义。不贴大段代码，只贴关键的几行。）

### 2 先红后绿的证据
红：（测试失败时的输出，原样粘贴）
绿：（源码改完后测试通过的输出，原样粘贴）

### 3 用例数量
（每个被编辑过的测试文件：编辑前 N 个 → 编辑后 M 个）

### 4 验收门输出
（gate.sh 的完整输出，原样粘贴）

### 5 逐项自检
（任务说明里「验收标准」的每一条，逐条写 完成 / 未完成 / 偏离，偏离的说明原因。不许只写一句“全部完成”。）

### 6 我拿不准的地方
（没有就写“无”。）
```

## 关于你的自我评价

调度方会用 `git diff`、独立复跑测试、以及把你的改动还原后看测试变不变红来验收，不会采信汇报里的结论。所以第 2、3、4 节的原始输出比任何总结都重要。如果某一项你没做到，直接写「未完成」，这比写「已完成」然后被验出来要好。
