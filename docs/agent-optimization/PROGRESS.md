### 07b · 撤销，不作为缺陷修

原本要把「钩子启动失败时放行」改成「拦截」。复核后撤销，两条理由：

1. **失败不阻断是写进契约的刻意设计**，不是疏漏。`agent-hooks.ts:18` 的模块注释原话：「**失败不阻断**：非零退出 / 超时 / 输出乱码都只记一条警告（`decision: block` 才是明确的拦）」。翻转它等于改产品行为，不是修 bug。
2. **失败也不是「静默」的**，我原先的描述夸大了。`agent-hooks.ts:294-300` 会记一条 warn 级日志，`agent.ts:2155-2164`（session_start）和 `:2736-2744`（user_prompt_submit）还会把「失败 N 条：<原因>」作为 status 事件写进会话轨迹，用户在界面上看得到。

真要让安全敏感的用户能选「失败即拦」，合理形态是给单条 hook 加一个 `failClosed` opt-in 配置，默认仍是放行。那属于新功能，和第四批那两个产品决策一起等用户拍板，不塞进缺陷修复批次。

07a 修掉的那个才是真缺陷：那不是「钩子失败了」，是**钩子根本没跑起来**，而且用户配的拦截逻辑一次都没执行过。

### 12 · 钉住当前轮的任务陈述（一次返工后通过）

缺陷：`agent-compaction.ts:40` 的注释写着「第一条消息一定是任务陈述」，这个前提只在单轮会话里成立。调用点 `agent.ts:2042-2048` 传进来的是整个会话历史，多轮时 `messages[0]` 是**第一轮**的问题；回合一长，从后往前的循环走不到当前轮的 user 消息就 break，模型于是看得到旧任务、看得到最近的工具结果，**唯独看不到这一轮要干什么**。

改法：额外钉住最后一条 user 消息，开销提前计入预算；**先剥尾部悬空工具结果、再补插任务陈述**（顺序反了的话，紧跟其后的那条工具结果检查不到，其 tool_call 已被裁掉，真实 OpenAI 兼容服务会 400）。

**第一轮交付门全绿但有真 bug，主 agent 读 diff 时发现并用探针坐实：**

- `taskIndex` 那个分支 `continue` 前没更新 `firstKept`，循环走过它再 break 时，末尾的补插判断仍然成立 → **同一条任务陈述出现两次**，`dropped` 计数也跟着偏小。
- 探针实测：同一组消息扫 7 档预算，60/80/100/120/150 都出现 2 次，200/300 正常。触发条件是「循环刚好放得下任务陈述、下一条大填充放不下就 break」，pi 自己那 3 条用例的预算恰好都不在这个区间。
- 返工把 `firstKept` 的更新挪到两个分支共用的位置，并补了一条用例钉住「只出现一次」。
- **返工后全参数空间扫描**（填充条数 × 尾部角色 × 尾部条数 × 预算 20–400，共 1872 种组合）：任务陈述恰好出现一次、占位之后不出现悬空工具结果、`dropped` 计数一致，**异常 0**。

### 02b · 凭据文件的覆盖源换成真实空文件（一趟通过）

02a 修的是「沙箱起不来」，当时用 `/dev/null` 当覆盖源，为的是保住 `bwrapArgs` 的纯函数设计（不探测、不碰文件系统，好在 macOS 上单测）。**当时就实测并记录了副作用**：沙箱内读那个文件拿到的是权限拒绝，不是空文件。

为什么这个副作用要修：`npm` 读 `.npmrc` 遇到 `EACCES` 会**报错退出**，而遇到「不存在或为空」会正常继续；`git` 读 `.git-credentials`、`curl` 读 `.netrc` 同理。沙箱一开，装依赖这类正常操作可能直接失败，**而失败原因看起来跟凭据毫无关系**——用户只会觉得「开了沙箱就装不上依赖」。安全效果两种写法一样（都读不到内容），差别全在可用性。

改法：新增 `sandboxBlankFile()`，数据目录下按需建零字节文件、已存在复用、**任何失败退回 `/dev/null`**（退化回当前行为，绝不能因为建不出文件又让沙箱起不来——02a 修的正是这个）。放数据目录而非临时目录：后者可能被系统清理，而沙箱启动时它必须存在。`bwrapArgs` 本身一行未动。

**主 agent 用真实 bwrap 做了 A/B 对照**：

| 覆盖源 | bwrap 退出码 | 沙箱内读 `.npmrc` |
|---|---|---|
| 真实空文件 | 0 | `rc=0`，`wc -c` 得 0 → 工具视作空文件，正常继续 |
| `/dev/null`（改前） | 2 | `Permission denied` → 工具报错退出 |

两种写法都没有泄漏凭据内容。
