## 背景：这是一次由我们自己的改动引起的回归

第 18b 条把单条工具结果的上限从固定 24000 字符改成「按上下文窗口的 25% 算」。8k 窗口下上限从 24000 变成 6144。

这个改动是对的（一条工具结果本来就不该吃掉大半个窗口），但它让这个冒烟脚本的第 7 项断言变红了：

```
✗ 任务中途触发过上下文压缩（摘要或裁剪） — []
```

实测对照（都在本机跑过）：

- 基线提交 24199d4 上跑：**全部通过，退出码 0**
- 当前分支上跑：**这一项失败**
- 把 `TOOL_OUTPUT_WINDOW_SHARE` 临时改回 1（等价于旧的 24000 上限）：**又通过了**

所以因果很明确。

原因：脚本第 415 到 417 行的注释写着「`-8k` 后缀把窗口钉在 8192，第 7 节『大输出把 8k 窗口顶穿』的压缩断言依赖这个数字」。这个场景只有**一个**大输出（第 316 行的 `bash seq 1 30000`，17 万字符）。旧上限下它被截到 24000 字符、约 6000 token，一条就把 8k 窗口顶穿，压缩立刻触发。新上限下它只有 6144 字符、约 1500 到 2000 token，占窗口两成左右，**一条顶不穿了**。

把窗口调小也没用——上限是按窗口比例算的，比例不变。我试过 4k 和 2k，两个都还是红。

## 要做什么

**让这条任务重新真的触发压缩，走「多条大输出累积」这条路**。那本来就是压缩要对付的真实情形：一条结果不该顶穿窗口，但十几步下来累积起来会。

具体做法你自己定，下面是约束：

1. **不许削弱任何现有断言**。第 7 项必须真的变绿，不能改成「发生过或没发生过都行」这种。
2. **不许改 `AGENT_COMPACT_MODE`、`SERVER_CTX_SIZE`、模型 id 后缀**去凑——那是绕过问题，要靠场景本身产生足够的上下文。
3. 建议路线：让桩服务在报告写完之前**多发几次带大输出的工具调用**（比如再来两三条不同的 `bash` 命令，各自输出很长）。步数上限在第 422 行 `AGENT_MAX_STEPS: "12"`，需要的话可以调大，但要在注释里说明为什么。
4. **注意第 541 行那条断言**：「重发没有重跑已经成功的工具（bash 只执行了 1 次）」。如果你新增了别的 `bash` 调用，这条会误报。它的**真实意图**是「被重发的那一次调用没有被重复执行」，所以允许你把它改成只数 `seq 1 30000` 这一条命令的执行次数，语义不变。改了要在汇报里说明。
5. 顺手把第 415 到 417 行那段注释改准确：现在「一条大输出顶穿窗口」的说法不再成立，要写清压缩是靠多条大输出累积触发的，以及为什么不能靠调小窗口来凑（上限随窗口等比缩放）。
